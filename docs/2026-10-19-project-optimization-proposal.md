## 1. 项目现状与评估边界

当前架构为浏览器 → WebSocket → Node 服务 → USB CDC → A/C 板 → CAN 电机。已有动态登记电机、通道绑定、网页/单电机遥控、麦轮/四轮全向遥控、PID 参数记忆、实时转速波形和多层回归测试，应作为迁移基线。

已检查 `motor_bench_host` 的页面、样式、界面状态、串口服务、协议、绑定恢复和波形代码，并抽查 A 板电机测试台固件及 A/C 板目录结构。已使用独立服务的未连接开发板页面检查 1440×900 和 390×844 布局，没有打开真实串口、驱动电机或烧录固件。

已通过的基线检查：

- `npm test`：现有协议及相关自测通过。
- `npm run test:waveform`：16 项波形历史与通道绑定测试通过。
- `npm run test:waveform:server`：真实 Node/WebSocket 服务与模拟串口的恢复回归通过。

上述结果不等同于全部回归、长时间性能测试或硬件验收。现有测试中部分项目直接匹配源码文本，迁移时应改为验证对应行为，不能仅为通过检查保留旧函数名和页面结构。

| --- | --- | --- |

## 2. 可选路线

| 路线 | 内容 | 取舍 |
| --- | --- | --- |
| A：原生前端模块化 | 保留 HTML/CSS/JS，重排布局并拆分模块 | 改动较小，适合继续维持少量工作区；增加记录、回放和测试流程后仍需维护较多手工状态同步 |
| B：前端分阶段组件化（推荐） | Vue 3 + TypeScript + Vite，复用 Node 桥接、现有协议和经过验证的业务规则 | 初期迁移成本较高，更适合本次持续扩展；必须按流程迁移并保留回归能力 |
| C：先做桌面安装包 | 将界面与串口服务打包为桌面工具 | 启动更方便，但会引入安装、原生依赖和升级维护；建议界面及服务稳定后再评估 |

推荐 B，分阶段交付。技术选型服务于连接状态、表单和多工作区的维护需求；不因为采用框架而重写所有模块。若实验室后续主要由熟悉原生 JS 的成员维护，也可以采用 A，下面的交互、状态和验收要求仍然成立。

Vue 官方提供 TypeScript 支持及 Vite 项目脚手架；Vite 的打包不能替代类型检查，采用 B 时应单独运行 `vue-tsc`。参考：[Vue TypeScript 文档](https://vuejs.org/guide/typescript/overview.html)、[Vite 生产构建文档](https://vite.dev/guide/build.html)。

## 3. 界面和操作流程

定位为实验室仪器工作台，桌面电脑优先，同时支持平板和手机查看及必要操作。建议延续深色基础，提高文字对比、数值字号和布局秩序；蓝色用于主要操作，红色集中用于停机和严重故障，运行状态用颜色加文字表达。主题切换可后置。

### 3.1 工作区结构

- **固定顶栏**：服务、串口、板端状态摘要，当前控制来源，以及全局急停。急停不弹确认框；反馈区分“已请求全停”“板端已禁用输出”和“失联、结果未确认”。
- **控制台**：电机/通道列表、选中电机的目标与实测数值、运行/停机、实时波形。将运行控制与波形放在相邻位置；多通道可切换紧凑总览。
- **调试分析**：PID、波形扩展、参数对比和后续测试任务。基础视图中保留明确入口，专业视图展开更多内容，两种视图共享状态和板端事实。
- **测试记录**：记录列表、曲线回放、导出与备注；在相应功能完成后出现。
- **设备与诊断**：串口设置、固件信息、登记清单、连接诊断、接线帮助和事件日志。

桌面端使用左侧通道列表、中央控制与波形、右侧可展开参数面板。手机使用单通道详情和任务切换，优先展示当前电机与运行状态；急停持续可见。未连接时用连接引导替代大面积空波形和禁用表单。

### 3.2 基础操作闭环

推荐流程：连接开发板 → 登记/选择电机 → 确认通道与控制环 → 输入目标 → 使能运行 → 观察与停机。

- 串口列表显示可取得的设备描述，提供最近使用项；识别信息不足时不假定某个 COM 口就是测试板。
- 登记前检查型号、总线、ID 和已知冲突，提交后显示板端结果。成功登记后引导选择空闲通道，不自动启动电机。
- 电机名称支持备注，例如“左前轮 · M3508 · CAN2 / ID1 · 通道0”，同时保留硬件身份。
- 未完成前置条件的操作给出具体原因和下一步，避免用户点击后才发现未连接或未绑定。
- 将长篇 CAN 说明收进上下文帮助；实际冲突直接显示在有关字段旁。显示的是登记清单，不把它称为自动发现的物理电机列表。
- 区分“准备下发的目标”和“板端当前目标”；输入、已发送和板端已确认状态各有明确反馈。
- 将“归零”改成含义明确的“目标设为 0”，避免与编码器零点校准混淆；“暂停波形”持续标明电机运行不受影响。
- 控制方式切换保留全停、回中、重新使能要求；底盘配置用 FL/FR/RL/RR 位置示意和方向预览，减少纯下拉表单中的轮序错误。

### 3.3 PID 与专业调试

- 保留可发现的 PID 入口，基础视图默认收起参数，专业视图直接展开。
- 分开显示“本地编辑值”“最近读回板端值”“型号默认值”，支持差异高亮和明确的应用结果。
- 保留现有 PID 记忆并迁移旧数据；本地参数按电机身份及控制环存储，记录版本，损坏时回退并提示。
- 参数模板支持命名、复制、导入和导出，不能把浏览器中保存的值当作当前板端生效值。
- 控制环决定目标量、单位和有效范围。DJI 转子 rpm、DM rad/s、位置角度及电流原始量分别表达；输出轴转速仅在用户配置减速比后派生。

## 4. 前端与服务改造

### 4.1 前端边界

建议拆为连接管理、命令服务、设备状态、通道控制、控制来源、PID、波形、测试记录和通用界面组件。高频遥测历史与表单状态分开管理，避免每个数据包触发整个工作台重绘。

状态至少覆盖：服务离线、服务在线但串口关闭、串口打开但板端未确认、板端在线、板端无应答，以及各通道未绑定、绑定中、已绑定、运行、离线。板端事实、用户编辑草稿和待确认操作分别保存。

第一阶段继续使用现有线协议；复用解析器、绑定恢复规则和有界波形历史。浏览器使用的共享协议定义与 Node 专用 Buffer 编解码应明确分层，迁移前覆盖关键行为。

构建后由现有 Node 服务提供前端静态资源，保持单个常用访问地址与离线使用能力。设计开发阶段可独立启动前端工具。需要配置构建、类型检查、代码规范和关键回归的统一入口。

### 4.2 命令与连接可靠性

- 服务端统一校验通道、型号、总线、控制环、数值有限性与范围，并捕获命令处理错误；前端校验只用于改善体验。
- 浏览器至服务加入请求关联与超时管理，减少重复提交及迟到结果覆盖新操作。线协议未携带关联标识的能力限制要明确，不能假装已彻底解决。
- WebSocket 自动重连采用退避，重连后先取状态快照并同步。自动恢复观察能力，运行/使能指令不得重放。
- 多页面采用一个控制者、其余观察者的规则，并提供明确的主动接管流程。控制权失效时全停；观察者退出不应影响控制者。相关页面关闭逻辑和回归一起调整。
- 全停指令优先处理；连续目标更新合并为最新值，离线时不积压稍后重放的控制指令。
- 串口打开、关闭和重连按会话串行管理，避免多页面并发操作导致状态错配。
- 保留并完善现有心跳和失联保护，界面显示停止原因；日志记录命令、确认、控制来源和连接事件。
- 本机访问保持默认方式。若确实需要局域网控制，再把来源校验、会话访问控制和观察权限纳入该范围。

### 4.3 性能改进原则

现有波形已限制历史为 60 秒/6000 点，并约每 50ms 绘制，不能将有界缓存和节流当作全新功能。先测量 8 通道下的主线程、内存与帧耗时，再决定是否将数组裁剪改为环形缓冲、采用绘制抽样或进一步优化。

隐藏页面和冻结显示时减少绘制；长时间记录交给有容量限制的独立记录模块。先保留现有 Canvas，是否更换图表库取决于缩放、游标和多曲线的实际需求。

| P0 | 任务化布局、连接引导和明确的运行状态 | 基础操作更短、更易理解 | 前端，可兼容当前固件 |
| P0 | 统一输入校验、命令超时、板端结果与草稿分离 | 避免误把请求当作成功 | 前端 + Node；完整确认需协议支持 |
| P0 | 达妙真实在线检测与失联处理 | 纠正当前在线状态语义 | 达妙驱动/固件 + 回归 + 实物验证 |
| P0 | 型号、控制环、单位和容量说明统一 | 避免错误量纲和能力预期 | 前端 + 文档；服务/固件校验同步评估 |
| P1 | 场景配置保存及 JSON 导入导出 | 换电脑、换电机、重启后减少重复设置 | 前端 + Node，可继续使用现有协议 |
| P1 | PID 预设与本地/板端差异对比 | 更容易复现实验参数 | 前端为主 |
| P1 | CSV 记录、事件日志和离线回放 | 把瞬时调试变成可复查的实验 | 前端 + Node |
| P1 | 多通道转速对比、游标和缩放 | 提升电控调试效率 | 前端；跨单位曲线使用独立坐标轴 |
| P1 | 底盘轮序与反向的可视化配置 | 减少装配和配置错误 | 前端，实际方向需低速验收 |
| P1 | 无硬件演示模式 | 方便培训、UI 开发和故障复现 | 模拟通信，与真实串口互斥并持续标识 |
| P2 | 绑定应答、通道清单、能力协商和板端会话标识 | 可靠恢复并兼容不同固件能力 | 协议 + Node + A/C 固件 |
| P2 | 有边界的阶跃、斜坡、正反转和定时测试 | 自动执行重复实验 | 固件优先保证执行/停止时序，前端发起并记录 |
| P2 | 超调、稳定时间、稳态误差计算 | 将 PID 对比量化 | 有效测试片段、采样条件和误差带定义 |
| P2 | 按型号验证的告警与保护阈值 | 将异常提示与停机策略关联 | 必须先确认有效遥测及量纲，保护落在固件 |
| P3 | 桌面启动器/安装包 | 降低安装和启动门槛 | 稳定版前端与 Node 服务之后评估 |

配置恢复必须先展示差异，经用户应用后登记/绑定；不保存运行使能状态，不在重连后自动恢复输出。浏览器保存的 PID 与恢复到板端的配置需要区分。

记录建议包括时间、板端固件版本、会话、电机身份、控制环与单位、目标与实测、PID 快照、连接及操作事件和备注。当前时间轴是主机接收时间；需要更精确的动态响应分析时再扩展板端采样时间戳，不把网页接收时间当作精确采样时间。

自动测试必须限定幅度、时长和结束策略，支持立即取消，失联中止，并在结束后明确停止；初期不加入自动 PID 整定。温度、电流和转矩保护只能基于实际支持且经过校验的数据；当前字段不足时明确“不支持”，不编造功率、效率或真实扭矩结论。

## 6. 固件和工程维护

- A/C 板中的电机测试台代码存在平行维护结构。先比较公共业务代码与板级差异，再抽取真正相同的控制、协议和测试逻辑；USB、串口、引脚、时钟和板级初始化保留各板适配。
- 协议升级增加明确版本/能力信息，旧固件继续开放其已支持功能，不根据界面选项假定板端支持新命令。升级应在停止状态进行。
- 当前工作目录包含嵌套的 `RM-MotorBench` 副本；先比对差异并确认主副本，再提出归档方案，本次不删除目录。
- 当前 Git 尚无提交，且已有大量暂存文件。实施前应先确认并保存基线；本次不替用户提交、重置或修改这些暂存内容。
- 增加可复现的启动说明、依赖/运行时要求、示例配置和统一测试入口；是否增加 CI 取决于代码托管环境。
- 更新 README 中过时的数量、流程和命令说明，接线与排障内容放进设备帮助并保持单一事实来源。

## 7. 实施顺序与验收

采用独立里程碑，分别处理界面、分析工具和协议固件，避免一次迁移所有层。

### 里程碑一：确认界面与操作闭环

产出控制台、PID 面板、手机布局的可评审原型，包含未连接、空清单、已绑定、运行、无应答及急停未确认状态。确认后再进入业务实现。

验收重点：基础操作的下一步明确；PID 入口可发现；目标设为 0、停止输出和暂停曲线含义清楚；急停始终可见。

### 里程碑二：交付新前端与服务可靠性改进

按连接 → 登记/绑定 → 控制来源 → 运行 → PID → 波形顺序迁移，兼容当前线协议；完成统一状态、校验、重连、控制权和关键行为回归。达妙在线检测作为独立固件修正安排实物验收。

验收重点：已有功能保持可用；重连不会启动电机；显示配置不会改变板端绑定；旧 PID 记忆可迁移；8 通道身份不混淆；错误有原因及恢复路径。

### 里程碑三：交付记录与调试效率功能

配置模板、PID 对比、CSV、事件日志、多通道波形、回放和演示模式按使用频率逐项交付。

验收重点：导出数据含单位和配置上下文；回放绝不下发控制指令；参数模板导入可预览；演示与真实设备持续可辨识；所有新增历史有容量边界。

### 里程碑四：协议、固件与自动测试升级

交付绑定应答和查询、能力协商、停止原因及板端时间信息；再实现有边界的测试序列和评价指标。A/C 板分别构建并完成实物测试。

验收重点：分别验证网页/遥控/底盘控制、USB 断开、服务退出、遥控器失联、电机反馈丢失、重复操作和旧固件兼容；保护与执行时序通过实物结果验收。
